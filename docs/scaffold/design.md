# scaffold — 設計ドキュメント

縦書き日本語小説エディタ「shippitsu」の**プロジェクト雛形（スキャフォールド）構築**タスクの仕様書。

---

## 目的・背景

### プロダクトの全体像

macOS 用の**縦書き日本語小説エディタ**を新規開発する。想定ユーザーは小説執筆者（本プロジェクトのオーナー）。オーナーは Swift の知識を持たないため、開発は Claude によるバイブコーディングで進める。

**動機:**

Word 等の既存アプリでは、原稿の文字数・行数の指定が煩雑である。とくに macOS 版 Word には Windows 版にある「文字数と行数を指定する」機能が無く、投稿規定（例:「1行40字 × 1ページ40行」）に合わせた執筆がしづらい。

そこで、**1行の文字数と1ページの行数を直接指定できる縦書きエディタ**を自作する。Windows 版 Word の「文字数と行数を指定する」ダイアログに相当する体験を、縦書き日本語組版の品質を保ったまま提供することがプロダクトのゴールである。

### 今回のタスクのスコープ

**今回作るのはスキャフォールド（プロジェクトの雛形）のみ。** エディタ本体の機能実装（原稿用紙グリッド、ルビ、縦中横、ファイル入出力、書き出し等）はすべて後続タスクとする。

したがって本ドキュメントの「要件」「仕様」セクションは、スキャフォールドの範囲に限定して記述する。プロダクト全体像に関する記述はこの「目的・背景」セクションに留める。

### なぜスキャフォールドを独立したタスクにするか

1. **技術的な急所の検証に着手できる土台を作るため** — 本プロジェクトの最大のリスクは「縦書き表示 + 日本語 IME 入力」が期待どおり動くかどうかに集中している。この検証自体は**後続タスクで行う**（D-6 により、本タスクの完成定義は「空のウィンドウが起動する」までとした）。本タスクの役割は、その検証にすぐ着手できるビルド可能な土台を用意することである。
2. **バイブコーディングの土台を固めるため** — Claude がファイルを追加・削除しながら実装を進めるため、その操作が安全に行えるプロジェクト構成を最初に決めておく必要がある。構成方式の選択は後から変更するとコストが高い。

| ID | 要件 |
|----|------|
| NFR-1 | **Claude による編集の安全性** — プロジェクト定義ファイルは人間・Claude の双方が読み書きできるテキスト形式であること。破損リスクの高い巨大な機械生成ファイルを Claude が直接編集する運用にしないこと |

- **`NSTextView` の配置・縦書き設定・日本語 IME の動作検証**（D-6 により後続タスクへ。本タスクではウィンドウは空のままとする）
- 原稿用紙グリッド（文字数 × 行数指定）の実装
- ルビ、縦中横、圏点、傍線などの組版機能
- ファイルの保存・読み込み、書き出し（PDF / テキスト / 縦書き印刷）
- 設定画面、テーマ、フォント選択 UI
- コード署名・公証・配布パッケージング（要件としては道を塞がないが、今回は実施しない）
- アプリアイコンのデザイン

## 仕様

> **注意:** 本セクションは未決事項 1〜10 の決定（D-2〜D-11）を反映して確定済み。以降の仕様変更は「決定事項」への追記とセットで行う。

### S-1. プロジェクト構成

構成方式は XcodeGen（D-2）、ターゲット構成はアプリ本体 + テストの 2 つ（D-7）で確定。**本セクションは外形的な構成（仕様レベル）のみを規定し、具体的なファイル名・ディレクトリ階層の細部は `impl.md` の管轄とする。**

| 項目 | 仕様 |
|------|------|
| プロジェクト定義 | リポジトリルートに `project.yml` が存在し、これが人間・Claude が編集する唯一のプロジェクト定義ファイルである（NFR-1） |
| 生成物 | `project.yml` から `.xcodeproj` を生成する。`.xcodeproj` は生成物であり Git 追跡対象に含めない（D-8） |
| ターゲット | アプリ本体ターゲット（内部名 `Shippitsu`）と、テストターゲットの 2 ターゲット構成 |
| ソースの取り込み | ソースはディレクトリ単位でまとめ、`project.yml` がディレクトリを丸ごとスキャンする形にする。ファイルの追加・削除でプロジェクト定義の手作業修正が発生しないこと（FR-4） |
| ドキュメント | `docs/scaffold/design.md`（本ファイル）と `docs/scaffold/impl.md`（実装フェーズ前に作成） |

### S-2. ビルド・実行の外部インタフェース

スキャフォールド完成後、以下の操作がコマンドラインで動作することを仕様とする（XcodeGen 採用に伴い、`xcodegen` によるプロジェクト生成 → `xcodebuild` によるビルド・実行という流れになる。具体的なコマンド列は `impl.md` の管轄）。

| 操作 | 期待される振る舞い |
|------|-------------------|
| セットアップ | プロジェクト定義からビルド可能な状態を作る。1 コマンドで完結すること |
| ビルド | コマンドライン 1 発でビルドが通る。エラーは標準出力に出る |
| 実行 | コマンドライン 1 発でアプリが起動する |

### S-3. 起動時の振る舞い

1. アプリを起動すると、ウィンドウが 1 枚表示される。
2. ウィンドウにはアプリ名がタイトルとして表示される。
3. メニューバーにアプリ名が表示され、`アプリ名 > 終了`（Cmd+Q）でアプリが終了する。
4. ウィンドウを閉じるとアプリが終了する（単一ウィンドウアプリとして扱う。将来の複数原稿タブ対応は後続タスク）。

### S-4. ウィンドウ内の表示内容

**空のウィンドウのみ**とする（D-6）。

- ウィンドウ内にはコンテンツを配置しない。
- `NSTextView` の配置、縦書き設定、日本語 IME の動作検証は**本タスクの範囲外**であり、後続タスクで行う（NFR-6 / スコープ外）。

### S-5. 動作確認手順（受け入れ基準）

以下の 4 項目をすべて満たした時点をスキャフォールドの「完成」とする（D-6 / D-9 / D-10）。

| # | 基準 | 根拠 |
|---|------|------|
| 1 | **ビルドが成功する** | D-6 |
| 2 | **アプリを起動するとウィンドウが 1 枚表示され、Cmd+Q で終了できる** | D-6 |
| 3 | **`xcodebuild test` が成功する**（プレースホルダのテスト 1 件が緑になる） | D-9 |
| 4 | **SwiftLint の警告が 0 件、かつ swift-format による整形差分が 0 件** | D-10 |

上記以外（縦書き表示・IME 入力・原稿用紙グリッド）は受け入れ基準に含めない。

**充足状況（2026-08-24 時点）: 4 項目すべて充足済み。** 基準 1 / 3 / 4 は機械的に確認済み、**基準 2 はユーザーによる実機の目視確認で 2026-08-24 に充足を確認**した（詳細な確認結果は `impl.md` の「5. 実装状況」および 6-1 のチェックリストを参照）。

> ⚠ **教訓（後続タスクへ / 受け入れ基準の変更ではない）: 基準 2 は「実機で目視するまで満たしたと判定できない」項目である。**
>
> 基準 2 について、実装完了後にユーザーが実機で起動したところ、**ウィンドウが 1 枚も開かず、メニューバーにアプリ名は出るが終了項目が無く ⌘Q も効かない**という不具合（S-3.1 / S-3.3 を満たさない状態）が判明した。原因は AppKit 固有の暗黙の前提（`@main` を `NSApplicationDelegate` 準拠クラスに付けても、nib を使わない構成ではデリゲートのインスタンスが生成されず `applicationDidFinishLaunching` が一度も呼ばれない）で、実装側の修正で解消済み（技術詳細は `impl.md` 2-2 / 5 章）。
>
> **重要なのは、この不具合がコードレビュー 5 レンズとドキュメントレビュー 3 巡をすべてすり抜けたことである。** 該当コードは文法上正しく、ビルド・テスト・SwiftLint・swift-format のすべてが通っていた。**「コードを読む」「ビルド・テスト・lint が通る」だけでは検出できない類の問題が存在する**（今回は "起動経路が nib の有無に依存する" というフレームワーク側の暗黙の前提）。したがって **UI を持つ変更については、機械的な検証がすべて緑でも「実機での目視確認が済むまで完成と判定しない」**運用を、後続タスクでも維持する。S-5 が基準 2 を機械確認に置き換えず目視確認のまま残しているのは、この性質のためである。
>
> **本注記は受け入れ基準そのものを変更していない**（4 項目は D-6 / D-9 / D-10 のまま）。

### S-6. ドキュメント運用

- 本 `design.md` は仕様・要件の唯一の情報源とする。会話で決まったことは必ずここに反映する。
- 実装フェーズに入る前に `docs/scaffold/impl.md` を作成し、構成・技術的判断・実装ステップ・コミット分割案を記述する。
- `impl.md` の作成・更新時は、書いたエージェントとは別のエージェントによるドキュメントレビューを即座に実施する（運用規約の中核ルール）。

## 決定事項

### D-1. 技術選定: Swift + AppKit（2026-07-27 決定）

**決定内容:** 実装言語を Swift、UI フレームワークを AppKit（macOS ネイティブ）とする。Electron / Tauri（Web 技術）、Flutter、Qt、Java 系はいずれも採用しない。

**理由:**

1. **Core Text が縦書きを一級市民として扱う唯一のプラットフォームであること**
   - Core Text は Apple の文字組版エンジン。縦書きに必要な機能が標準 API として揃っている:
     - ルビ — `CTRubyAnnotation`（振り仮名を本文に添える標準 API）
     - 縦中横 — `vert` / `vrt2` フォントフィーチャ（縦書き中で数字などを横に寝かせる組版）
     - 日本語禁則処理 — `CTTypesetter` に内蔵（行頭に句読点が来ないよう調整する処理）
   - 他プラットフォームではこれらを自前実装する必要があり、小説エディタとしての組版品質を担保できない。

2. **日本語 IME との連携が決定的であること**
   - Electron / Tauri + CSS `writing-mode: vertical-rl` では、`contenteditable` 上で以下の破綻が起きる:
     - 変換中の未確定文字列が縦方向に流れない
     - 変換候補ウィンドウが縦書きキャレットに追従しない
     - 選択範囲のハイライトが横書き前提の矩形になる
   - AppKit では `NSTextInputClient`（アプリと IME をつなぐ標準プロトコル）を OS 側が実装しているため、これらが**追加コストゼロ**で正しく動く。日本語入力が主用途である本プロジェクトでは、この差が決定的である。

3. **他の候補の除外理由**
   - Flutter — 縦書き未サポート。
   - Qt / Java 系 — 日本語組版の品質が不足しており、小説の版面として使えない。

**トレードオフとして受け入れたもの:** macOS 専用となり、Windows / Linux への展開はできない。ユーザーの利用環境が macOS のみであるため許容する。

### D-2. プロジェクト構成方式: XcodeGen（2026-07-27 決定）

**決定内容:** `project.yml`（テキスト）から `.xcodeproj` を生成する **XcodeGen** 方式を採用する。SPM 単独（`Package.swift`）や `.xcodeproj` の直接作成は採用しない。導入に `brew install xcodegen` が必要。

**理由:**

- プロジェクト定義が短いテキストファイルであり、Claude が安全に読み書きできる（NFR-1）。
- ソースはディレクトリ自動スキャンのため、ファイル追加時にプロジェクト定義の修正が不要（FR-4）。
- 最終的に `.xcodeproj` が生成されるため、将来の署名・公証・App Store 配布を Xcode 標準フローで行える（NFR-4）。SPM 単独ではこの部分を自前スクリプトで組む必要があり、そのリスクを回避した。
- 日常の開発は `xcodegen` → `xcodebuild` でコマンドライン完結し、ユーザーが Xcode を開く必要がない（NFR-2 / NFR-3）。

**トレードオフとして受け入れたもの:** `xcodegen` の追加インストール（初回 1 コマンド）が必要になること。

### D-3. アプリ名・Bundle Identifier（2026-07-27 決定）

**決定内容:**

| 項目 | 値 |
|------|-----|
| 表示名（メニューバー / Dock / Finder） | **執筆** |
| 内部ターゲット名・生成物名 | **`Shippitsu`** |
| Bundle Identifier | **`com.ayatsukiaya.shippitsu`** |

**理由:** 日本語小説エディタとして表示名は日本語が自然である一方、日本語パスに起因するツール・スクリプトのトラブルを避けるため、内部名は英字とする。

> **注意（実装者向け）:** Bundle ID は推奨として提示した仮値 `com.konoreiji.shippitsu` ではなく、**ユーザーが指定した `com.ayatsukiaya.shippitsu`** が正である。取り違えないこと。

### D-4. 最低対応 macOS バージョン: macOS 26 以降（2026-07-27 決定）

**決定内容:** Deployment Target を **macOS 26** とする（選択肢 a）。

**理由（ユーザーの判断）:** 将来的に配布する場合も、セキュリティホールのリスク等を考えると最新 OS のみを対象とすれば良いという認識であるため。

**トレードオフとして受け入れたもの:** macOS 26 未満のマシンでは動作しない。その代わり可用性チェックの分岐が不要になり、コードが単純に保たれる。

### D-5. Lint / Formatter: SwiftLint + swift-format の両方を導入（2026-07-27 決定）

**決定内容:** 選択肢 **C（両方）** を採用する。整形は **swift-format**、内容の静的チェックは **SwiftLint** が担う。スキャフォールド段階から両方を導入する。

> ⚠ **推奨と異なる選択がなされた項目。** design.md 上の推奨は **B（swift-format のみ。SwiftLint はコード量が増えてから後付け）** であったが、ユーザーは **C** を選択した。**後続の作業者・サブエージェントは推奨側（B）に引きずられず、C を前提に実装すること。**

**理由（ユーザーの判断）:**

- TypeScript のプロジェクトでも Lint と Formatter はスキャフォールドの一部として導入しているため、本プロジェクトでも同様に扱う。
- プロジェクトを進める中でユーザー自身もコードレビューを行う（現時点で Swift は読めないが、他言語の知識をもとに実施する）。

**受け入れたトレードオフ:** `brew install swiftlint` の追加インストールと、初期のルール調整コストが発生すること。

### D-6. スキャフォールドの完成定義: 空のウィンドウが起動するまで（2026-07-27 決定）

**決定内容:** 選択肢 **a** を採用する。「ビルドが通り、ウィンドウが 1 枚表示され、Cmd+Q で終了できる」時点を完成とする（受け入れ基準は S-5）。縦書き `NSTextView` の表示・日本語 IME 検証・原稿用紙グリッドは、いずれも本タスクの範囲外とする。

> ⚠ **推奨と異なる選択がなされた項目。** design.md 上の推奨は **b（縦書き `NSTextView` + 日本語 IME の入力・変換まで動くこと）** であったが、ユーザーは **a** を選択した。**後続の作業者・サブエージェントは推奨側（b）に引きずられず、a を前提に実装すること。**「技術的な急所を早期に検証する」という推奨 b の論拠は、本タスクには適用されない。

**理由（ユーザーの判断）:**

- この段階では最低限の app の形だけを作り、検証は次タスクで行いたい。
- 検証結果によって「このタスクで実装したものをリバートする必要が出る」ようなものは作らない、という最小限のイメージ。

**影響:** S-4 / S-5 を上記で確定。縦書き・IME 検証をスコープ外に明記し、リバート前提の先取り実装を禁じる制約を NFR-6 として起こした。

### D-7. テストターゲット: 含める（2026-07-27 決定）

**決定内容:** 選択肢 **A** を採用し、アプリ本体とは別にテストターゲットを `project.yml` に定義する。アプリ本体 + テストの 2 ターゲット構成とする（S-1）。

**理由（ユーザーの判断）:** ユーザーの Swift ナレッジ不足を担保するためにも、テストはマストであるため。

**補足:** テストケースの中身は後続タスクで埋める。本タスクではターゲットが存在しビルドできること（FR-6）までを扱う。

### D-8. Git 初期化とブランチ運用（2026-07-27 決定 / 2026-07-28 に D-12 で補完）

**決定内容:**

- 本スキャフォールドタスクの中で `git init` と `.gitignore` の作成まで行う（選択肢 A）。
- **`feat/init-scaffold` ブランチを作成し、この design.md に対応する作業はすべてこのブランチで行う。**
- `.gitignore` にはビルド中間生成物（`.build/`、`DerivedData/`）、`.DS_Store`、ユーザー固有の Xcode 設定を含める。**生成物である `.xcodeproj` も追跡対象に含めない**（`project.yml` から再生成できるため）。

### D-15. `main` に空コミットを 1 個置いて PR の base にする（2026-08-24 決定）

**決定内容:** 未決事項 15 の選択肢 **A** を採用する。

1. **`main` に空コミット（ファイルを 1 つも含まないコミット）を 1 個だけ置く**（`git commit --allow-empty`）。これにより `main` が ref として実体を持ち、リモートへ push できる。
2. **空コミットはファイルを含まないため、`main` にプロジェクトのファイルが乗ることはない。** D-12 の「`main` にファイルを置かない」という意図はそのまま維持される（置かれるのは中身ゼロの目印 1 個だけ）。
3. **PR は base = `main` / head = `feat/init-scaffold` として作成する**（D-12 の 3 のとおり）。空コミット側にファイルが無いため、**PR の差分にはプロジェクト全体（`.gitignore` / `.claude/` / `docs/` / `project.yml` / `Sources/` / `Tests/`）が現れ**、ユーザーの意図「PR で完全な差分を見せる」は完全に満たされる。

**理由（ユーザーの判断）:** D-12 の「`main` にコミットを一切置かない」と「base = `main` の PR を出す」は**技術的に両立しない**（git のブランチはコミットを指す目印にすぎず、コミットが 0 件の `main` は ref として存在しないため、`gh pr create --base main` は base を解決できず必ず失敗する）。ユーザーの 2 つの意図（`main` にファイルを置かない / PR で完全な差分を見せる）を**どちらも満たせる**のは A のみであり、選択肢 B（PR を作らない）はユーザーの明示指示「PR で完全な差分を見せてください」に反するため選べなかった。

**D-12 との関係（重要）:**

| 論点 | D-12（旧） | D-15（現在有効） |
|------|-----------|-----------------|
| `main` に置くもの | コミットを**一切**置かない | **空コミット 1 個のみ**置く。**ファイルは置かない** |
| `main` にファイルを置くか | 置かない | **置かない（変更なし）** |
| すべてのコミットを `feat/init-scaffold` に乗せるか | 乗せる | **乗せる（変更なし）** |
| PR の base / head | `main` / `feat/init-scaffold` | **同左（変更なし）** |
| PR の差分 | プロジェクト全体 | **同左（変更なし）** |

**D-15 が改めたのは D-12 の 1 の文言（「コミットを一切置かない」）だけであり、D-12 の意図・目的は一切変更していない。** 旧文言は「変更履歴」に記録した。**`main` の用意方法と PR 作成手順の正は本項（D-15）である** — D-12 だけを読んで「`main` にコミットを置かない」と解釈すると PR を作成できないため、必ず本項を併せて読むこと。

**トレードオフとして受け入れたもの:** 履歴に「ファイルを含まない空のコミットが 1 つある」状態になること。空コミットは git で一般的に使われる手法であり、これ以外の影響はない。

**実装への反映:** `impl.md` の Step 11 のブロック注記を解除し、手順を「`main` で空コミット作成 → push → `feat/init-scaffold` を push → PR 作成」に更新済み。**`feat/init-scaffold` 側の 6 コミットには一切影響しない**（すでに作成・push 済みだが手戻りは発生しない）。
