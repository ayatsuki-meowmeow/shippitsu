# ci — 設計ドキュメント

GitHub Actions による **CI（継続的インテグレーション）構築**タスクの仕様書。対応する issue は [#16](https://github.com/ayatsuki-meowmeow/shippitsu/issues/16)。

---

## 目的・背景

### なぜ CI を入れるか

現状、ビルド・テスト・SwiftLint・swift-format の実行は**すべてローカルでの手動実行**である（`docs/scaffold/impl.md` 3 章）。`docs/scaffold/design.md` の受け入れ基準 S-5 は 4 項目からなり、そのうち **1（ビルド成功）・3（テスト成功）・4（lint 警告 0 件 / 整形差分 0 件）は機械的に検証できる**。これらを PR ごとに自動実行すれば、以下が担保される。

1. **人間の実行忘れがなくなる** — 手動実行は「やったつもり」で漏れる。とくにドキュメント修正のついでにコードを触った回などに漏れやすい。
2. **バイブコーディングの前提を守る** — 本プロジェクトは Claude がビルドエラーを自力で確認・修正することを前提にしている（`docs/scaffold/design.md` NFR-2）。CI があると、Claude のローカル環境固有の事情に依存せず「クリーンな環境で通る」ことまで確認できる。
3. **後続タスクの安全網になる** — 縦書きレイアウト・組版機能といった今後の実装は回帰しやすい。CI がないと、機能追加のたびに既存機能の破壊を目視で追うことになる。

### スコープの位置づけ

本タスクは**開発基盤の整備**であり、プロダクトの機能実装ではない。`docs/scaffold/design.md` のスコープ外セクションには記載がなく、issue #16 も「ドキュメントに記載のある項目ではなく提案である」と明示している。**ユーザーが不要と判断すれば本タスクごと取りやめてよい。**

### CI で代替できないもの（重要）

`docs/scaffold/design.md` S-5 の**基準 2（アプリを起動するとウィンドウが 1 枚表示され、⌘Q で終了できる）は CI で代替できない。** 基準 2 は「**人がウィンドウを見て判断する**」ことを内容とする基準であり、CI には見る人間がいないためである。

> **補足（誤認を避けるための注記）:** これは「ランナーでアプリが起動できない」という意味では**ない。** `docs/scaffold/impl.md` Step 8 のとおり、macOS の unit test は `TEST_HOST` 経由でアプリを起動するため、**テスト実行中に実際にウィンドウが 1 枚開く**。CI で代替できないのは起動そのものではなく、**描画結果（タイトル文字列・メニューバーの見た目・⌘Q の実挙動）の目視判断**である。

さらに同 S-5 には、**スキャフォールドで実際に起きた不具合の教訓**が記録されている — `AppDelegate` が生成されずウィンドウが 1 枚も開かない不具合が、コードレビュー 5 レンズ・ドキュメントレビュー 3 巡・ビルド・テスト・SwiftLint・swift-format の**すべてをすり抜けた**。

したがって本タスクの目的は「目視確認を CI で置き換えること」では**ない**。**機械的に検証できる 3 項目を自動化して目視確認に集中できるようにすること**である。CI の導入によって「UI を持つ変更は実機の目視確認が済むまで完成と判定しない」という運用は**一切緩めない。**

## 要件

### 機能要件

| ID | 要件 |
|----|------|
| FR-1 | PR に対して、`docs/scaffold/design.md` S-5 の機械検証可能な 3 項目（ビルド成功 / テスト成功 / lint 警告 0 件・整形差分 0 件）が自動実行されること |
| FR-2 | いずれかの検証が失敗した場合、PR 上で失敗として表示され、失敗した検証と原因がログから特定できること |
| FR-3 | ローカルで実行するコマンド（`docs/scaffold/impl.md` 3 章の早見表）と CI が実行するコマンドが一致していること。CI だけが通る／ローカルだけが通る状態を作らないこと |
| FR-4 | CI の実行環境が、本プロジェクトの `deploymentTarget: macOS 26.0`（D-4）を満たすこと |
| FR-5 | CI の設定がリポジトリ内のテキストファイルとして管理され、Claude が編集できること |

### 非機能要件

| ID | 要件 |
|----|------|
| NFR-1 | **CI の失敗原因が切り分け可能であること** — 「自分の変更が壊した」のか「ツールが勝手に更新されて壊れた」のかを区別できること。区別できないと、Claude が自力でエラーを修正するという前提（scaffold NFR-2）が成立しなくなる |
| NFR-2 | **ユーザーの手作業を最小化すること**（scaffold NFR-3 の継承）— CI の日常運用でユーザーが GitHub の管理画面を操作する必要が無いこと。初回のリポジトリ設定のみ例外を許容する |
| NFR-3 | **実行時間が実用的であること** — PR を出してから結果が出るまでの待ち時間が、開発ループを阻害しない範囲に収まること |

### スコープ外（今回やらないこと）

- **アプリの実機起動確認・スクリーンショット取得**（ランナーに GUI セッションが無いため技術的に不可能。上記「CI で代替できないもの」を参照）
- **CD（継続的デリバリー）** — ビルド成果物の配布、リリース自動化、署名・公証の自動化は issue [#18](https://github.com/ayatsuki-meowmeow/shippitsu/issues/18) の管轄
- **テストカバレッジの計測・可視化**（テスト自体がプレースホルダ 1 件のみの現状では意味が無い。issue [#15](https://github.com/ayatsuki-meowmeow/shippitsu/issues/15) の進行後に再検討する）
- **依存パッケージの自動更新**（Dependabot 等）— 現状 Swift Package の依存が 0 件のため不要
- **複数の macOS / Xcode バージョンでのマトリクスビルド** — 対応環境が macOS 26 以降の 1 系統のみ（D-4）のため不要

## 仕様

> 本セクションは未決事項 1〜3 の判断（→ D-1 / D-2 / D-3）を反映して**確定済み**。以降の仕様変更は「決定事項」への追記とセットで行う。

### S-1. 実行タイミング（D-1）

| イベント | 対象 | 目的 |
|---|------|------|
| `pull_request` | base が `main` の PR | マージ前に受け入れ基準（S-2）を検証する |
| `push` | `main` | マージ後の `main` が壊れていないことを担保する（squash merge で差分が変わる場合に効く） |
| `workflow_dispatch` | 手動 | CI 自体のデバッグ・再実行 |

**変更パスによる除外（`paths-ignore`）は行わない**（D-1）。ドキュメントのみの PR でも CI を走らせる。

### S-2. 検証項目

CI が実行する検証は以下の 5 つとする。`docs/scaffold/impl.md` 3 章の早見表と Step 5〜8 に対応する。

| # | 検証 | 対応する S-5 の基準 |
|---|------|------------------|
| 1 | プロジェクト生成が成功する | （`docs/scaffold/design.md` S-2 のセットアップ。以降の前提） |
| 2 | ビルドが成功する | 基準 1 |
| 3 | テストが成功する | 基準 3 |
| 4 | SwiftLint の警告が 0 件 | 基準 4 |
| 5 | swift-format の整形差分が 0 件 | 基準 4 |

具体的なコマンド列は `impl.md` の管轄とする（FR-3 により、ローカルの早見表と同一のコマンドを使う）。

### S-3. 実行環境（D-2）

| 項目 | 仕様 |
|------|------|
| ランナー | `macos-26`（GitHub-hosted / arm64）。FR-4 を満たすランナーは他にもある（`macos-26-intel` / `macos-26-large` / `macos-latest`）が、**ローカルと同じ arm64 であること**を理由に本ランナーを選ぶ |
| Xcode | **バージョンを明示して選択する。** ランナーの既定バージョンに依存しない |
| SwiftLint / XcodeGen | **Mint でバージョンを固定する。** 固定するバージョンはリポジトリ内の `Mintfile` を唯一の情報源とする |
| swift-format | Xcode のツールチェーン同梱のものを使う（`xcrun swift-format`）。Xcode を固定することで連動して固定される。**ランナーにプリインストールされている別物の「SwiftFormat」は使わない**（下記の注意を参照） |
| ローカルとの一致 | ローカルと CI で同一バージョンのツールが使われること（FR-3）。実現方法は `impl.md` の管轄 |

**具体的なバージョン番号の正は `Mintfile` とする**（S-3 の表のとおり）。`impl.md` にもバージョン表を置くが、それは**作成時点のスナップショット（記録）**であり情報源ではない。**バージョンの更新は独立した PR として明示的に行う**（D-2）。

### S-4. 失敗時の扱い（D-3）

| 項目 | 仕様 |
|------|------|
| PR 上の表示 | S-2 の検証が 1 つでも失敗したら、PR 上で失敗として表示される（FR-2） |
| マージの可否 | **CI が成功していない限り `main` へマージできない**（必須チェック / ブランチ保護） |
| 例外 | **admin によるバイパスを許可する。** CI 自体が壊れた場合にユーザーが手動でマージできる逃げ道を残す |
| 設定の実行者 | ブランチ保護の設定は **Claude が `gh` API で実行してよい** |

## 前提の確認結果（2026-08-24 調査 / 判断ではなく事実の記録）

issue #16 に「ランナーの macOS / Xcode バージョンが `deploymentTarget: macOS 26.0` を満たすかを最初に確認する。満たさない場合、CI 導入自体が成立しない」と記した前提を確認した。**結論: 満たしており、CI 導入は成立する。**

| 項目 | 確認結果 | 出典 |
|------|---------|------|
| `macos-26` ランナーの提供状況 | **GA**（2026-02-26 に一般提供開始）。`macos-26` は arm64、`macos-26-intel` / `macos-26-large` は x64。`macos-latest` は `macos-26` arm64 を指す | [GitHub Changelog](https://github.blog/changelog/2026-02-26-macos-26-is-now-generally-available-for-github-hosted-runners/) / [actions/runner-images](https://github.com/actions/runner-images) |
| ランナーの OS / Xcode | macOS 26.5.2 (25F84)、Xcode は 26.0.1〜26.6 の 7 バージョンが導入済みで **26.6 が既定** | [macos-26-arm64-Readme.md](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md) |
| macOS SDK | 26.0〜26.5 が導入済み。`deploymentTarget: macOS 26.0` を満たす | 同上 |
| ローカル環境との差 | ローカルは macOS 26.3 / Xcode 26.6 / macOS SDK 26.5。**Xcode の既定バージョンはランナーと一致している** | 実測（2026-08-24） |
| 課金 | 本リポジトリは **public**（D-13）のため GitHub-hosted ランナーの利用は無料。macOS ランナーの分単位課金（private リポジトリでは 10 倍消費）の対象外 | GitHub の課金仕様 |
| `xcodegen` | ランナーに**プリインストールされていない**。導入が必要 | 同 Readme の導入済みソフトウェア一覧 |
| `swiftlint` | ランナーに**プリインストールされていない**。導入が必要 | 同上 |
| `mint` | ランナーに**プリインストールされていない**。導入が必要（D-2 で Mint を採用したため CI 側にも導入ステップが要る） | 同上 |
| `swift-format` | Xcode 26 のツールチェーンに同梱されており `xcrun swift-format` で利用できる。**2026-08-26 の初回 CI 実行でランナー上の実在を確認済み**（`xcrun swift-format --version` → `6.3.0`。ローカルと一致） | ローカル・ランナーとも 6.3.0 |
| Homebrew | プリインストール済み（6.0.13）。`xcodegen` / `swiftlint` の導入経路として使える | 同 Readme |

> ⚠ **`swift-format` の同名別物に注意。** ランナーには「**SwiftFormat 0.62.1**」がプリインストールされているが、これは Nick Lockwood 版の `swiftformat` であり、本プロジェクトが使う **Apple の `swift-format`**（`xcrun swift-format`、ローカル 6.3.0）とは**別のツール**である。設定ファイルもルールも互換性がない。CI で誤って前者を呼ぶと、整形差分の判定が `docs/scaffold/design.md` D-5 / D-10 の意図と食い違う。**必ず `xcrun swift-format` を使う。**

## 決定事項

> 本タスク固有の決定は **D-1〜D-4**（D-1〜D-3 は 2026-08-24、D-4 は 2026-08-25 決定）。番号は本タスク内の通し番号であり、`docs/scaffold/design.md` の D-1〜D-15 とは別系統である（混同しないこと）。
>
> なお、本タスクは `docs/scaffold/design.md` の以下の決定を**前提として継承**する（本タスクで覆さない）:
>
> - **D-4** — 最低対応 macOS バージョンは macOS 26 以降（FR-4 の根拠）
> - **D-5 / D-10** — SwiftLint と swift-format の両方を使い、警告 0 件・整形差分 0 件を受け入れ基準に含める（S-2 の 4・5 の根拠）
> - **D-9** — 受け入れ基準にテストの実行を含める（S-2 の 3 の根拠）
> - **D-11** — 開発ツール・依存パッケージのインストールは Claude が実行する
> - **D-13** — リポジトリは `ayatsuki-meowmeow/shippitsu`（**public**）
> - **S-5 の教訓** — 機械的検証がすべて緑でも、UI を持つ変更は実機の目視確認が済むまで完成と判定しない

### D-1. 実行タイミング: PR + `main` への push + 手動実行。パス除外はしない（2026-08-24 決定）

旧・未決事項 1 の選択肢 A を採用した。仕様は S-1 のとおり。

**理由:**

1. 本リポジトリは public のため Actions の実行は無料であり、実行回数を節約する動機が無い。`paths-ignore` による除外で得られるのは**待ち時間の短縮のみ**である。
2. その対価として「**コード変更があるのに CI が走らない**」という最悪の失敗モードのリスクを負う。本プロジェクトは lint の通過まで受け入れ基準に含める（scaffold D-10）ほど機械的検証を重視しており、取りこぼしのリスクを避ける方が方針と整合する。
3. **D-3 で必須チェックにするため、`paths-ignore` との併用は「チェック未実行でマージがブロックされる」既知の落とし穴を踏む。** 除外しないことでこの問題自体が発生しない。
4. `main` への push も対象にすることで、squash merge によって PR 時点と差分が変わる場合にも `main` の健全性を担保できる。

**トレードオフ:** ドキュメントのみの PR でも毎回 macOS ランナーが起動し、数分の待ち時間が発生する。本プロジェクトは `design.md` / `impl.md` の更新が頻繁でドキュメントのみの PR が一定割合を占めるため、この待ち時間は実際に発生する。**待ち時間が苦痛になった時点で `paths-ignore` の導入を再検討する**（後から足すのは容易）。

### D-2. ツールのバージョンを Mint で固定する（2026-08-24 決定）

旧・未決事項 2 について、**Mint（`Mintfile`）で SwiftLint / XcodeGen のバージョンを固定し、Xcode も明示指定する**。仕様は S-3 のとおり。

**理由:**

1. **SwiftLint はマイナー更新で新ルールが追加され、既存コードが警告を出すようになることがある。** 本プロジェクトは `--strict` で警告 0 件を受け入れ基準にしている（scaffold D-10）ため、警告を許容するプロジェクトより赤化しやすい構造にある。固定しないと、**自分の変更と無関係な PR が突然赤くなり、原因の切り分けが手作業になる**（NFR-1）。
2. **これらのツールは `Shippitsu.app` に一切同梱されない**ビルド時ツールであり、アプリに載る依存パッケージとは異なりセキュリティ更新の緊急度が低い。現時点で Swift Package の依存は 0 件である。
3. **固定は「更新しない」ことを意味しない。** 更新は独立した PR として行い、新ルールへの対応をその PR に閉じ込める。これは TypeScript における lockfile ＋ Dependabot の運用と同じ考え方である。
4. **Homebrew では固定できない。** `swiftlint` / `xcodegen` に versioned formula は存在せず（`node@20` のようなものが無い）、`brew install` は常に最新を取得する。Swift ツールのバージョン管理には Mint が該当し、これが TypeScript の `package-lock.json` に最も近い（Mint の作者は XcodeGen と同じ yonaskolb）。
5. **Xcode の固定は追加コストがほぼゼロ。** ランナーには 26.0.1〜26.6 の 7 バージョンが導入済みで、`xcode-select` で選ぶだけである。ランナーの既定 Xcode は予告付きで変更される実績があるため（26.0.1 → 26.2）、明示しておく価値がある。swift-format は Xcode 同梱のため、これで連動して固定される。

**トレードオフ:**

- バージョンを上げる作業が手動になる。ただし D-2 の目的からすれば、**これは失われた自動化ではなく「意識的な作業への変換」**である。
- **Mint はツールをソースからビルドするため、初回の CI 実行に時間がかかる**（とくに SwiftLint）。`~/.mint` のキャッシュで 2 回目以降は解消する見込みだが、**実測での確認が必要**であり、NFR-3 に対するリスクとして `impl.md` に記録する。

**選択の経緯（Claude の説明誤りの記録）:** 本項目には一度「固定しない」という判断が入ったが、その判断は **Claude が提示した誤った前提**に基づいていた。訂正内容は以下の 2 点であり、訂正後に改めて判断いただいた結果が本決定である。

| 誤り | 訂正 |
|------|------|
| 「固定しないと失敗原因の切り分けが**できない**」 | 言い過ぎ。正しくは「**自動では判別できず、赤くなるたびに手作業で追う必要がある**」。CI ログにバージョンを出せば事後追跡は可能 |
| 選択肢の例示に `brew install swiftlint@0.65.0` と記載 | **実在しないコマンド。** Homebrew に当該 versioned formula は無く、この方法では固定できない（上記 4） |

あわせて「TypeScript では新バージョンが来たらセキュリティ懸念があるので上げるが、Swift は違うのか」という論点について、**違わない**（TypeScript でも eslint / prettier 等の開発ツールは lockfile で固定されており、固定は例外ではなく既定である）ことを整理した。上記 2・3 がその内容にあたる。

### D-3. CI を必須チェックにする。設定は Claude が実行してよい（2026-08-24 決定）

旧・未決事項 3 の選択肢 A を採用した。仕様は S-4 のとおり。

**理由:**

1. 受け入れ基準を満たさないコードが `main` に入らないことを、運用ではなく**機構として保証**できる。
2. とくに **Claude がマージ操作を代行する場面**で効く。Claude が「たぶん大丈夫」と判断してマージすることを機構的に防げる。
3. D-1 で `paths-ignore` を使わないため、「除外された PR がチェック未実行でマージできない」という併用時の落とし穴を踏まない。

**例外:** **admin によるバイパスを許可する**（`enforce_admins` を有効にしない）。CI 自体の不具合でマージが完全に止まる状態を避けるため、ユーザーが手動でマージできる逃げ道を残す。

**設定の実行者:** ブランチ保護の設定は **Claude が `gh` API で実行してよい。** リポジトリ設定の変更はツールのインストール（scaffold D-11）とは性質が異なり D-11 では読み切れないため、本決定で明示的に許可した。**本決定が許可するのは本タスクに必要なブランチ保護の設定のみであり、リポジトリ設定全般への白紙委任ではない。**

**設定値の詳細は D-4 を参照。**

### D-4. ブランチ保護は `strict: true`（マージ前に base の最新化を要求する）（2026-08-25 決定）

旧・未決事項 4 の選択肢 B を採用した。D-3 の内側の設定値を確定させるもので、D-3 自体は変更しない。

**確定した設定値:**

| 設定項目 | 値 |
|---------|---|
| `required_status_checks.contexts` | `["verify"]`（`impl.md` 2-3 のジョブ名） |
| `required_status_checks.strict` | **`true`** |
| `enforce_admins` | `false`（D-3 の例外規定） |
| `required_pull_request_reviews` | `null`（レビュアーが実質 1 人のため、有効にすると自分の PR をマージできなくなる） |
| `restrictions` | `null` |

**理由:** 個別には緑でも組み合わせると壊れる変更（semantic conflict）が `main` に入る余地を残さない。D-1 で `main` への push でも CI が走るため事後検知はできるが、**そもそも壊れた状態を `main` に作らない**ことを優先した。

**トレードオフ（ユーザーの推奨と異なる選択であることの記録）:** Claude の推奨は `strict: false` だった。**`strict: true` では、`main` が進むたびに既存の PR は base を取り込んで CI を再実行しない限りマージできない。** PR が同時に複数開いている場面では、片方をマージするたびにもう片方で待ちが発生する（D-1 によりドキュメントのみの PR でも CI が走るため、その待ちは毎回発生する）。現状は PR が逐次に進む運用のため影響は小さいが、**同時進行の PR が増えて待ち時間が問題になった場合は `strict: false` への変更を検討する**（後から変更できる設定であり手戻りは無い）。
